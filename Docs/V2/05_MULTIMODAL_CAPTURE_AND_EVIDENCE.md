# 05. Multimodal Capture and Evidence

## 1. 목표

사용자는 다음 자료를 한 번에 또는 따로 입력할 수 있어야 한다.

- 직접 쓴 텍스트
- 클립보드 이미지
- 휴대폰 화면 캡처
- 카메라 사진
- 책·문서 스캔
- 대화 캡처 여러 장
- 음성·영상·녹취
- PDF와 일반 파일

입력 방식이 달라도 같은 문서·개체·사건 모델로 구조화한다.

## 2. Capture Bundle 규칙

한 번의 저장 행동은 하나의 `Capture Bundle`이다.

```text
Capture Bundle
├── user note
├── source item 1: image
├── source item 2: image
├── source item 3: audio
└── client metadata
```

기본값은 하나의 기록으로 분석하되, 서로 무관한 자료가 명확하면 여러 `Document Proposal`을 만든다. 자동 분할은 원본 묶음을 변경하지 않는다.

### 자동 분할 조건

- 서로 다른 제목·출처·날짜의 독립 스크랩
- 하나의 녹취 안에서 명확히 구분되는 별도 세션
- 여러 파일이 서로 다른 작품이나 장소를 가리킴

### 분할하지 않는 조건

- 한 장소의 음식 사진·지도·메뉴판
- 한 운동의 요약·심박·구간 화면
- 한 대화의 연속 캡처
- 한 책의 표지와 인용 페이지

저신뢰 분할은 하나로 유지하고 `split_suggestion`만 제공한다.

## 3. 첨부 역할

첨부에는 복수 역할을 배정할 수 있다.

| 역할 | 의미 | 예시 |
| --- | --- | --- |
| `primary_source` | 문서의 본문 자체 | 책 페이지, 녹취 |
| `evidence` | 구조 필드의 증거 | 운동 화면, 영수증 |
| `subject_identifier` | 대상을 식별하는 단서 | 게임 표지, 영화 포스터 |
| `context` | 경험의 배경 | 음식·여행 사진 |
| `illustration` | 글을 보여 주는 이미지 | 에세이 첨부 사진 |
| `quotation_source` | 외부 문장의 원본 | 책의 한 줄, 게시물 캡처 |

역할은 원본을 변경하지 않고 `document_source_links`에 기록한다.

## 4. 이미지 분석 단계

### I-01. 원본 저장

- R2 원본 key
- SHA-256
- MIME type
- 크기와 방향
- EXIF 원본
- 캡처 내 표시 순서

### I-02. 파생 파일

- UI preview WebP
- OCR용 방향 보정본
- 저신뢰 영역 crop
- thumbnail

파생 파일은 재생성 가능하며 원본과 구분한다.

### I-03. 시각 유형 판정

- app_screen
- chat_screen
- web_clip
- document_scan
- book_page
- cover_or_title
- food_photo
- place_photo
- receipt_or_menu
- general_photo
- unknown

이 값은 처리 모드이며 사용자 콘텐츠 유형과 다르다.

### I-04. OCR·레이아웃 추출

- 원문 텍스트 블록
- 블록별 bounding box
- 읽기 순서
- 표·레이블·값 관계
- 아이콘·로고·단위
- OCR 신뢰도

### I-05. 도메인 해석

3.6 Flash가 OCR과 시각 정보를 함께 사용해 사건, 개체, 필드를 제안한다.

## 5. OCR 데이터의 세 층

### Raw OCR

모델이 화면에서 읽은 그대로의 텍스트와 레이아웃이다. 수정하지 않는다.

### Normalized Text

명백한 OCR 오류, 줄 연결, 숫자 형식을 정규화한 버전이다. 변경 내역을 기록한다.

### Structured Values

검색·필터·계산에 쓰는 typed property다.

```text
Raw OCR: 평균 페이스 6'14"/km
Normalized: 평균 페이스 6분 14초/km
Structured: 374 sec/km
```

문학 작품과 인용문은 exactness가 중요하므로 `Raw OCR`을 기본 표시하고 교정문을 별도 제공한다.

## 6. 이미지 영역 근거

모든 OCR 기반 필드는 `source_item_id + normalized bounding box`를 가진다.

```json
{
  "source_item_id": "src-image-1",
  "locator_kind": "image_region",
  "locator": {
    "x": 0.12,
    "y": 0.18,
    "width": 0.31,
    "height": 0.09,
    "coordinate_space": "normalized"
  },
  "quote": "5.02 km"
}
```

UI는 필드를 클릭하면 원본에서 영역을 강조한다.

## 7. 운동 화면

### 추출 후보

- 운동 유형
- 날짜·시작·종료 시각
- 거리
- 지속 시간
- 페이스·속도
- 심박수
- 칼로리
- 케이던스
- 파워
- 고도
- 세트·반복·중량
- 경로
- 개인 기록

앱별 화면 스키마를 고정하지 않는다. 화면 레이블과 값의 관계를 읽고 필드 레지스트리와 대조한다.

### 계산값

평균 페이스처럼 다른 값에서 계산할 수 있는 필드는 `calculated`로 저장하고 입력 근거와 식을 연결한다.

## 8. 대화 캡처

### 순서 복원

우선순위:

1. 사용자 업로드 순서
2. 화면 속 날짜·시각
3. 겹치는 메시지 내용
4. 파일 생성 시각

순서가 바뀌면 AI 결정과 신뢰도를 기록한다.

### 중복 제거

연속 캡처의 겹치는 메시지는 하나의 발화로 투영하되 모든 이미지 근거를 연결한다.

### 구조화

- 발화자
- 메시지 시각
- 원문
- 주장·반박
- 합의·결정
- 약속·기한
- 언급된 과거 사건
- 대화 중 새로 발생한 사건
- 미해결 쟁점

AI 해석과 직접 발언을 분리한다. 의도·성격·관계 상태는 명시적 근거 없이 사실로 저장하지 않는다.

## 9. 스크랩과 웹 캡처

분리할 데이터:

- 외부 원문
- 사용자 주석
- 출처 후보
- 작성자·작성일
- 화면에 보이는 URL
- 핵심 주장
- AI 요약·주제

출처가 화면에 없으면 2.5 검색 요청을 만들 수 있지만, 정확히 일치하지 않으면 `unresolved_source`를 유지한다.

## 10. 음식·장소 사진

사진에서 관찰 가능한 것과 사용자 평가를 분리한다.

### 관찰 가능

- 음식 종류 후보
- 재료·조리법 후보
- 플레이팅
- 공간·메뉴판·상호 단서

### 사진만으로 확정 불가

- 실제 맛
- 사용자 만족도
- 정확한 가격
- 방문 목적
- 정확한 장소

사용자 메모, EXIF 위치, 지도 캡처, 상호 단서가 함께 있을 때만 장소 개체를 resolve한다.

## 11. 게임·영화·책 식별 이미지

1. OCR로 제목·로고·저자·플랫폼 단서를 추출한다.
2. 시각 특징과 텍스트로 후보를 만든다.
3. 2.5 grounded search로 정확한 작품·판본·에디션을 확인한다.
4. 후보가 여러 개면 임시 개체와 review item을 만든다.

이미지만 올렸다고 소비 사건을 만들지 않는다.

- 표지 저장: 발견·스크랩
- “오늘 시작”: 시작 사건
- “다 봤다”: 완료 사건
- 감상·평점 존재: 리뷰·평가

## 12. 책 페이지와 인용

저장 요소:

- raw OCR
- normalized text
- 페이지 번호
- 장 제목
- 강조 영역
- 책 개체 후보
- 사용자 주석
- 인용 범위

OCR 교정은 원문처럼 보이게 덮어쓰지 않는다. 정확한 인용이 불확실하면 `needs_review`를 표시한다.

## 13. 오디오·영상·녹취

### Source

- 원본 파일
- 녹음 시각·길이
- 자동 녹취
- 화자 구간
- 타임코드

### Knowledge

- 참여 인물
- 화제
- 사건
- 결정
- 약속과 기한
- 주장
- 관련 개체

근거 locator는 타임코드를 사용한다.

```json
{
  "locator_kind": "transcript_time",
  "locator": {"start_ms": 861000, "end_ms": 888000},
  "quote": "다음 주까지 초안을 보내기로..."
}
```

화자 이름이 불명확하면 `speaker_1`을 유지하고 사용자 확인 뒤 인물 개체와 연결한다.

## 14. 다중 첨부 결과 UI

처리 결과 화면은 다음을 제공한다.

- 원본 첨부 갤러리
- 원본/정규화 OCR 전환
- 추출 필드와 근거 하이라이트
- 생성된 문서·사건·개체 목록
- 분할·병합 제안
- 낮은 신뢰도 항목만 수정

사용자는 구조화 결과를 모두 검토하지 않아도 원문을 읽고 검색할 수 있다.

## 15. 실패 정책

| 상황 | 올바른 결과 |
| --- | --- |
| 흐린 이미지 | 원본 저장, 저신뢰 OCR, 미확정 |
| 잘린 제목 | 후보 여러 개 또는 unresolved |
| 화면 방향 오류 | 파생본 회전 후 재시도 |
| 대화 순서 불명 | 업로드 순서 유지, 경고 |
| OCR 숫자 충돌 | 두 후보와 근거 보존, 확인 요청 |
| 이미지 과다 | background 처리, 캡처 저장은 즉시 완료 |
| 분석 모델 실패 | 원본·미리보기 열람 가능, 재시도 큐 |

## 16. 모바일 입력

MVP 이후가 아니라 Capture MVP의 일부로 고려한다.

- 모바일 웹에서 카메라·사진 선택
- OS 공유 시트에서 이미지·URL 전달
- 클립보드 붙여넣기
- 여러 장 순서 변경
- 간단한 메모 추가
- 업로드 완료 후 앱을 닫아도 background 처리

PWA 또는 네이티브 wrapper 구현 방식은 개발 단계에서 결정하되, API 계약은 `Capture Bundle` 하나로 통일한다.
